# Review del review — estado real de Zapa-IA (2026-09-12)

Contraste de un review externo contra el código y los datos actuales. Cada afirmación se
verificó leyendo `features.py`, `score.py`, `cache.py`, `dedupe.py`, `compilado.py`, `cli.py`
y corriendo mediciones sobre el caché v4 (849 archivos, 11.205 ventanas). Donde el review
está mal, se dice. Donde tiene razón, se cuantifica.

## 0. Resumen

El review acierta en casi todo lo verificable, y en dos casos el problema es **peor** de lo
que sugiere. La tesis central —Zapa-IA está construido para responder "¿qué tan bien está
tocado?" cuando el objetivo es "¿hay acá una idea que vale la pena recuperar?"— es correcta
y el scorer actual ya tiene la mitad de la separación hecha (`creatividad` y `desarrollo`
existen), pero esa mitad está **sin validar**. El cuello de botella no es features ni
arquitectura: es que hay 3 positivos verificados y **cero negativos**. Todo lo que se
construya sobre `creatividad` o embeddings sin feedback humano es adivinar con más pasos.

Orden recomendado: (P0) arreglos de scoring que no requieren reprocesar, (P1) herramienta de
comparación A/B, después lo demás.

### Lo que el review no vio

- **`tempo` está cuantizado a 26 valores** en 11.205 ventanas (`beat_track` devuelve una grilla). `tempo_consistency` (55% de `DESARROLLO`) mide la varianza de una variable casi discreta: es gruesa.
- **`notas` pesa 0.15 en el score por default**, y penaliza exactamente lo que el objetivo quiere rescatar (riffs cromáticos, blues, disonancia intencional). Para el ranking de ideas tiene que ser 0. Hoy no lo es.
- **`creatividad` está sin validar.** Existe un A/B pendiente (`muestra_A` vs `muestra_B`, comparten 6 de 10 tramos). Nada debería construirse sobre esa dimensión hasta tener la respuesta.
- **Cada cambio de `features.py` cuesta ~2 h de reprocesamiento** (4 h con overlap). Los cambios de features deben **agruparse en un solo salto de `FEATURE_VERSION`**, no hacerse de a uno.
- **La detección de tema por nombre** (`temas_por_nombre`, 108 temas sobre 850) es hoy el mejor proxy de "identidad de idea" que hay, y sirve como etiqueta débil para el experimento de embeddings. El review propone embeddings para lo que los nombres ya resuelven parcialmente.

## 2. Ejecución vs. interés: ¿encaja con el scorer actual?

Sí, y con costo bajo. Las dimensiones ya existen; lo que falta es dejar de sumarlas en un
solo número.

```
ejecucion = TIMING + GROOVE + AFINACION + tonal_outlier   (SONIDO solo como veto)
interes   = CREATIVIDAD + DESARROLLO  (+ futuro: recurrencia de idea, novedad por embedding,
                                          preferencia humana aprendida)
```

`_group_score()` y `pesos_ejec` ya hacen todo el trabajo; es una reorganización de
`score.py` y tres presets en `compilado`:

| Perfil | Selección | Qué produce |
|---|---|---|
| `performances` | `ejecucion` alto | lo que hoy hace el sistema |
| `ideas` | `interes` alto, `ejecucion` ignorado, `tonal_outlier` = 0 | lo que el objetivo pide |
| `gems` | `interes` alto **y** `ejecucion` bajo/medio | lo que el sistema actual descarta sistemáticamente |

Riesgo: `interes` hoy descansa en `creatividad` (sin validar) y `desarrollo` (con
`tempo_consistency` gruesa). Separar los scores es barato y correcto, pero **el ranking de
ideas no va a ser confiable hasta que haya etiquetas** (§5). Hacerlo igual: sirve para
generar los pares del feedback.

## 3. Segmentos persistentes sin romper el caché

La tabla `windows(path, widx, start, feats JSON)` **ya es** una tabla de segmentos de
análisis. No hay que reemplazarla; hay que agregar alrededor. Todo aditivo, versionado con
`PRAGMA user_version`:

```sql
-- identidad de archivo más robusta (nullable, no rompe filas existentes)
ALTER TABLE files ADD COLUMN sha1_parcial TEXT;   -- primer+último MB + size
ALTER TABLE files ADD COLUMN drive_id TEXT;

-- embeddings por ventana, por modelo (varios modelos conviven durante el experimento)
CREATE TABLE embeddings (path TEXT, widx INTEGER, modelo TEXT, ver INTEGER,
                         vec BLOB, PRIMARY KEY (path, widx, modelo));

-- segmentos musicales presentados al usuario: varias ventanas, bordes libres
CREATE TABLE segmentos (id INTEGER PRIMARY KEY, path TEXT, start REAL, end REAL,
                        origen TEXT,            -- 'compilado' | 'feedback' | 'manual'
                        fver INTEGER, creado REAL);

-- feedback humano pareado (ver §5)
CREATE TABLE feedback (id INTEGER PRIMARY KEY, seg_a INTEGER, seg_b INTEGER,
                       eleccion TEXT,          -- 'A' | 'B' | 'ambos' | 'ninguno'
                       tags TEXT, fver INTEGER, ts REAL);

-- más adelante, cuando los embeddings estén entendidos
CREATE TABLE ideas (id INTEGER PRIMARY KEY, seg_representante INTEGER,
                    primera_vez REAL, ultima_vez REAL, n INTEGER);
CREATE TABLE idea_miembros (idea_id INTEGER, seg_id INTEGER, sim REAL);
```

`is_fresh()` pasa a comparar `mtime` **y** `size`; cuando exista `sha1_parcial`, ese manda.
Los archivos con `status='error'` se reintentan si cambió cualquiera de los tres.

## 4. Embeddings: qué tiene sentido para este dataset y esta máquina

Restricciones reales: macOS ARM, 18 cores, sin GPU discreta (MPS disponible), Python
**3.9.6** en el venv de TensorFlow (EOL desde 2025-10). Nada de PyTorch instalado.
Recomendación previa a cualquier modelo: **un segundo venv con Python 3.11** para el
experimento, sin tocar el de TF. Verificar versiones al momento de implementar.

| Candidato | Qué es | A favor | En contra |
|---|---|---|---|
| **Croma beat-sincrónico + correlación cruzada / DTW** (no neural) | el método clásico de detección de covers | invariante al timbre **por construcción**; mide literalmente "misma progresión / mismo riff"; cero dependencias nuevas; `chroma_cqt` ya se calcula | no captura groove ni melodía fina; sensible a transposición (se resuelve rotando el croma) |
| **MERT-v1-95M** (HF, PyTorch) | SSL específico de música | entrenado en música, captura armonía y ritmo; corre en CPU/MPS; ~400 MB | PyTorch + transformers; frames a 75 Hz → hay que agregar; sin validar en grabaciones caseras |
| **CLAP** (LAION, variante música) | audio-texto | permite búsqueda por texto ("groove funk lento"); semántico | pesado; entrenado en música producida, no ensayos; riesgo alto de agrupar por calidad de grabación |
| **OpenL3** (music, 512-d) | embedding de propósito general | maduro, TF/Keras | muy tímbrico: alto riesgo de que "misma sala" domine sobre "mismo riff" |
| **YAMNet embeddings** (1024-d) | ya instalado | costo cero de setup; sirve como baseline | AudioSet, no música; tímbrico; ya se descartaron sus clases por inútiles |

Lo que el review advierte —confundir similitud tímbrica con musical— es el riesgo #1 de
cualquier red, y en este corpus es agudo: la firma actual demostró que el "fondo común"
(sala + banda) domina todo. Por eso la línea de croma no neural **tiene que estar en el
experimento**: es la única representación que no puede equivocarse en esa dirección.

### Experimento controlado (antes de adoptar nada)

Subconjunto de ~60 archivos con relaciones conocidas:

- 5 pares de duplicados exactos (ya identificados: `Bossa`/`Bossa (1)`, etc.)
- 10 tomas de `fluyendo`, 10 de `kiki`, 10 de `epilepsia` (mismo tema, distinta toma, etiqueta por nombre)
- pares crudo/remaster (`zapadita fluyendo` vs `zapadita fluyendo remaster`): mismo material, distinta calidad
- 20 archivos de temas distintos al azar

Embeddings por ventana de 30 s, para 5 representaciones (firma actual, croma-DTW, YAMNet,
MERT, y OpenL3 o CLAP). Cinco métricas:

1. **Duplicados**: ¿el vecino más cercano es el duplicado? (debe ser 100%)
2. **Mismo tema**: precision@5 usando la etiqueta por nombre como verdad débil
3. **Invariancia a calidad**: sim(crudo, remaster) vs sim(crudo, otra toma del mismo tema). Si el remaster queda más lejos que otra toma, el embedding mide grabación, no música.
4. **Confusión tímbrica**: correlación parcial entre similitud y \|Δ centroid\|, \|Δ low_energy_ratio\|. Si la similitud se explica por timbre, es sala, no idea.
5. **Estructura intra-archivo**: en 3 archivos largos con cambio de canción conocido, ¿el embedding salta donde salta la canción?

Regla de decisión: adoptar la representación con mejor (2)+(3) y menor (4). Si croma-DTW
empata con la red, gana croma-DTW: sin dependencias, sin GPU, interpretable.

## 5. Feedback humano pareado: la implementación más simple

El dato clave de esta sesión: el usuario dijo "es difícil validar lo que decís" cuando se le
preguntó si `creatividad` elegía bien, y respondió sin dudar cuando se le dio un A/B. La
comparación pareada no es una preferencia de diseño: es la única forma en que se obtuvieron
etiquetas.

Dos modos, misma tabla:

**Escritorio** — `zapaia comparar --n 20`: elige pares, exporta dos clips de ~40 s, los
reproduce con `afplay` (macOS, sin dependencias), pregunta `A / B / ambos / ninguno / saltar`
más tags opcionales, guarda en `feedback` con ids de segmento y `fver`.

**Celular** — `zapaia comparar --lote 20 --drive`: genera `par_001_A.mp3`, `par_001_B.mp3`,
… y un `lote.txt`, los sube con `rclone` a la carpeta de Drive, y después
`zapaia feedback importar "001 A, 002 B, 003 ninguno"` parsea la respuesta tal como se la
escribe por WhatsApp. Es el flujo que ya se usó para `muestra_A`/`muestra_B`.

**Qué pares mostrar** (esto decide cuánta información da cada respuesta):

- 50%: dos segmentos de **temas distintos** con score compuesto parecido → máxima incertidumbre, máxima información
- 30%: al azar → calibra
- 20%: candidatos a *gem* (interés alto, ejecución baja) contra *performance* (ejecución alta, interés bajo) → responde directamente la pregunta estratégica del review

**Qué hacer con las respuestas**, por etapas:

1. Con 30–50 comparaciones: **Bradley–Terry** → score latente por segmento. Correlar con cada dimensión. Eso dice qué dimensiones predicen el criterio del usuario, y reemplaza el ajuste manual de pesos. También responde el A/B de `creatividad` de forma continua.
2. Con 150–300: regresión logística sobre diferencias de features → primer learning-to-rank. Antes de eso, no entrenar nada (coincido con el review).
3. Con embeddings validados: agregarlos como features. Cada fila de feedback guarda `fver`, así los modelos se reentrenan sin ambigüedad cuando cambian las features.

## 6. Roadmap incremental

Cada ítem preserva el caché y el pipeline existentes.

### P0 — Arreglos de scoring (sin reprocesar)

| Cambio | Impacto | Costo | Riesgo | Evidencia |
|---|---|---|---|---|
| Sacar `fuera_tono_picos` de `NOTAS` | medio | trivial | nulo | 23 valores únicos en 11.205 ventanas |
| Bajar `onset_dev_mad` a 0.15 en `TIMING` (era 0.40) | medio | trivial | bajo | mediana 0.227 vs 0.25 aleatorio; 74% ≥ 0.20 |
| Renombrar `NOTAS` → `tonal_outlier`; peso 0 en `interes` | alto (conceptual) | bajo | nulo | ρ=+0.50 flatness, −0.56 contrast; objetivo "hidden gems" |
| Composites `ejecucion` / `interes` + perfiles `performances/ideas/gems` | alto | bajo | bajo | §2; dimensiones ya existen |
| `find_groups`: union-find + centrado + recalibrar umbral | bajo | bajo | bajo | test sintético; firma cruda ~0.98 |
| `is_fresh`: comparar `size`; reintentar errores si cambió algo | bajo | trivial | nulo | `cache.py`; `uoho.mp3` nunca se reintenta |

### P1 — Feedback pareado (§5)

Impacto **alto** — es lo que desbloquea todo lo demás. Costo bajo (un comando, una tabla,
`afplay`, `rclone`). Riesgo bajo. Evidencia: 3 positivos, 0 negativos, `creatividad` sin
validar, A/B pendiente.

### P2 — Modelo de segmentos (§3)

Impacto medio ahora, alto después. Costo bajo (migración aditiva). Riesgo bajo si se hace
con `user_version` y sin tocar `windows`.

### P3 — Overlap + `FEATURE_VERSION` 5 (un solo reprocesamiento)

Agrupar en un solo salto: hop 15 s, `onset_dev` respecto de grilla de subdivisiones (16avos)
más consistencia de grilla (entropía del histograma de fases: síncopa tight = histograma
concentrado, timing flojo = plano), `tonal_outlier_eventos` (excursiones sobre umbral global,
no percentil), `tempo` continuo (autocorrelación del onset envelope en vez de la grilla de
`beat_track`). Antes de lanzar: arreglar los tres supuestos de §1.8. Impacto medio-alto.
Costo ~4 h de máquina + medio día de código. Riesgo medio (validar con `diag` sobre un
`--sample 40` antes del corpus completo).

### P4 — Experimento de embeddings (§4)

Impacto potencialmente alto, incierto. Costo 1–2 días. Riesgo medio: la probabilidad de que
la red agrupe por sala es real; por eso el baseline de croma. No procesar el corpus completo
hasta tener el resultado.

### P5 — Clustering de ideas / evolución cronológica

Solo con una representación validada en P4. Necesita fechas: hoy el corpus no tiene fecha
confiable (mtime de copias, nombres con "2018"/"25"). La cronología del review requiere
resolver metadata primero (P7 aporta `modified_time` de Drive, que tampoco es fecha de
grabación).

### P6 — Modelo de preferencia

Con ≥150 comparaciones. No antes.

### P7 — Ingesta desde Drive (manifest: `drive_id`, checksum, `modified_time`, `local_path`)

Cuando el pipeline sea estable. `rclone lsjson` da todo eso en una llamada.

### P8 — Escala a miles de archivos

Con la representación estable y el feedback funcionando. A 4 h por 850 archivos con overlap,
10.000 archivos son ~2 días de máquina: aceptable si se hace una vez.

## 7. Qué no hacer

Coincido con la lista del review. Agrego, desde la experiencia de esta sesión:

- **No cambiar `features.py` de a una feature.** Cada cambio son 2–4 h. Agrupar.
- **No optimizar `is_fresh` con hashes completos** antes de necesitarlos: 9 GB se leen en minutos, pero a 100 GB ya no.
- **No interpretar una dimensión por su nombre.** `sonido` premiaba silencio, `notas` mide banda ancha, `timing` es 40% ruido. Cada nombre es una hipótesis hasta que un humano la confirme.
- **No usar `epilepsia orgasmica.mp3` como held-out.** Está contaminado por diseño.
- **No descartar los nombres de archivo.** Son la mejor etiqueta débil de identidad de tema disponible, gratis.

## 9. P0 ejecutado (mismo día) — qué se hizo y qué se aprendió

Cambios de scoring, sin reprocesar audio:

- `fuera_tono_picos` fuera de `TONAL_OUTLIER` (queda como diagnóstico).
- `onset_dev_mad` 0.40 → 0.15 dentro de `TIMING`.
- `NOTAS` → `TONAL_OUTLIER`; `--w-notas` sigue funcionando como alias de `--w-tonal`.
- Composites `ejecucion` (timing, groove, afinacion, tonal_outlier) e `interes` (creatividad,
  desarrollo), y `--perfil balance | performances | ideas | gems` en `rank`, `eval` y
  `compilado`. Con `ideas`/`gems` el tramo dentro de cada archivo se elige por ejecución
  **limpia** (sin tonal_outlier): el mejor minuto y medio de una idea es el que se sostiene
  tocando, no el que evita cromatismos.
- `find_groups`: union-find (transitivo, verificado con cadena A~B~C sobre fondo aleatorio) y
  similitud **centrada**. Umbral recalibrado a **0.997**: duplicados exactos dan 1.0000,
  remaster de la misma toma 0.9978, tomas distintas del mismo tema ≤ 0.9935. Con 0.98 agrupaba
  `take 3 soft` con `take 4 soft` (falso positivo). Resultado: 11 grupos, los 5 exactos
  conocidos más 6 re-mezclas del mismo take (`mix2`, `gtm`, `ensayo medio`).
- `is_fresh` compara `size` además de `mtime`; `extract --reintentar-errores` fuerza los que
  fallaron.

### Lo que el eval reveló al aislar cada cambio

Sobre los 3 positivos held-out, percentil mediano de `balance`:

| composición de `balance` | mediana |
|---|---|
| timing + groove + afinacion + desarrollo | **83.3** |
| + tonal_outlier | 82.6 |
| + creatividad | 79.1 |
| las seis | 74.2 |

Cada dimensión sin validar que entra, **baja** las referencias humanas. Hay que decirlo: `notas`
(hoy `tonal_outlier`) y `creatividad` se agregaron en la sesión anterior **sin volver a correr
`eval` sobre el corpus completo**, y el default había quedado en 74.2 sin que nadie lo midiera.
Es exactamente el error que la regla 8 de `CLAUDE.md` prohíbe. `balance` vuelve a la mezcla
validada; `tonal_outlier` y `creatividad` viven solo en `performances`, `ideas` y `gems`.

Con n = 3 esto no prueba que esas dimensiones sean malas — prueba que **no están validadas**
y que las referencias disponibles (tomas elegidas para mezclar) las contradicen. Bajo `ideas` las
mismas referencias caen al percentil 40, y bajo `gems` al 34: consistente con que "elegida para
mezclar" mide ejecución, no interés. Es la pregunta que P1 tiene que responder con pares.

Dos observaciones más, para P1/P3:

- Bajar `onset_dev_mad` (justificado por estadística agregada: parecía ruido) costó ~8 puntos a
  `zapadita fluyendo remaster` (96 → 88). Con n = 3 no se revierte, pero queda anotado: el
  criterio 5 del review (correlación con decisiones humanas) debe pesar más que el 3 (estabilidad
  estadística) en cuanto haya suficientes pares.
- `interes` premia la duración: `queriendonebulosa zapada completa` (105 min, 200 ventanas) queda
  #2 en `ideas` porque `novedad_armonica` crece con la cantidad de secciones. Normalizar por
  duración o usar percentiles de novedad por ventana es tarea de P3.

## 8. Correcciones explícitas al review

Tres cosas que el review da por hechas y no lo están, o al revés:

1. "Análisis de estabilidad frente a parámetros" existe **solo para `band_sync`**. `fuera_tono`, `key_clarity` y `pulse_clarity` no fueron testeadas.
2. El problema de `dedupe.py` no es principalmente la transitividad: es que **compara vectores sin centrar**, con lo cual el umbral 0.9995 solo detecta re-encodes. La transitividad importa recién cuando el umbral baje.
3. La cuestión Drive está resuelta en la dirección correcta (core local, Drive como entrega), pero el review no menciona que **el MCP de Drive es inviable para subir audio** y que `rclone` usa un `client_id` compartido que deja de funcionar durante 2026.
